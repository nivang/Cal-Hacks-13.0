# Feedback for Coinbase

## Phase 2
- **x402 Python SDK has no manual-flow doc.** The examples use the auto-paying httpx wrapper (`x402HttpxClient`), which signs with no gap for a guard or human approval. We had to read the SDK source to find `x402HTTPClient.get_payment_required_response`, `x402Client.create_payment_payload` and `encode_payment_signature_header`. Workaround: payments.py drives these directly. Coinbase should document a "bring your own control flow" path and a pre-sign hook that can pause.
- **No way to sign one chosen requirement.** `create_payment_payload` picks from `accepts` itself, so we narrow `accepts` to one entry with `model_copy`. Coinbase should accept an explicit requirement or index, as the TS `signX402Payment(paymentRequired, index)` does.
- **CDP account needs a wrapper for x402.** `EvmLocalAccount(account)` then `EthAccountSigner` is required and undocumented together.
- **Quote expiry is `max_timeout_seconds` (300 here) on the requirement.** It is not tied to a human approval window, which matters for Phase 6.
- **x402 server typing:** `ExactEvmServerScheme` fails mypy against `x402ResourceServer.register` (`payment_flows` is typed `dict[str, dict[str, Sequence[str]]]` but expected `Mapping[str, PaymentFlowConfig]`). It works at runtime. We silence it with a targeted `type: ignore`. Coinbase should align the annotations.

## Intent binding
- **The seller's description is the best signal for "what is being bought", and it is easy to miss.** x402 v2 puts it in `PaymentRequired.resource` (`description`, `service_name`, `tags`), filled from the server's `RouteConfig`. Our demo sellers had sent the route path as the description until now. Workaround: Sentinel reads `resource` from the 402 and treats it as quoted, untrusted data for the intent judge. Coinbase should document `resource` as what a buyer side policy engine should check, and consider a signed or registry backed description (Bazaar) so a seller cannot claim to sell one thing and charge for another.

## Per user wallets
- **The x402 signer blocks the event loop.** `EthAccountSigner(EvmLocalAccount(account))` is the only way to hand a CDP account to x402, and x402's `ClientEvmSigner.sign_typed_data` is synchronous, so every signature is a blocking HTTP call to CDP's signing endpoint inside our async server. With one wallet per user and several users paying at once, one slow signature stalls every other request on that process. There is no async signer to swap in, so we kept it. Workaround: cap payments in flight (2 per user, 6 per process) so a stall stays bounded. Coinbase should ship an async x402 signer for CDP accounts (an `async sign_typed_data`, or an x402 signer built on `CdpClient` directly).
- **Account names are limited to 2 to 36 characters.** We wanted names that say whose wallet it is (an email or `user-<uuid>`), but `user-<uuid>` is 41 characters and emails can be anything. Workaround: the account name is the bare user uuid (36 characters), which also can never collide with the shared demo account `sentinel`. Coinbase should allow longer names or a separate metadata or label field, and document the limit next to `get_or_create_account`.
- **SDK analytics stalled calls.** The CDP SDK sends usage and error analytics by default; when that endpoint was slow, our CDP calls stalled with it. Workaround: the server sets `DISABLE_CDP_USAGE_TRACKING=true` and `DISABLE_CDP_ERROR_REPORTING=true` unless the operator sets them, and wraps lookups in a 15 second timeout. Coinbase should send analytics in the background so they can never delay an API call, and document the two variables.

## Escrow (auth-capture)
- **No Python SDK or facilitator for auth-capture.** x402 2.25.0 (latest) has the `escrow` payment flow table but no auth-capture scheme; @x402/evm 2.28.0 ships only a client (`AuthCaptureEvmScheme`); the x402.org facilitator's `/supported` lists exact, upto and batch-settlement only. Workaround: sentinel/escrow.py implements PaymentInfo hashing, the payer agnostic nonce, ReceiveWithAuthorization and the escrow calldata, checked against the contract's own `getHash`, and Sentinel's CDP account acts as operator and sends authorize, capture and void itself. Coinbase should ship the scheme in the Python SDK (client, server and facilitator) and support it on the CDP facilitator.
- **The EVM binding doesn't give the v1.1 ABI, and capture changed.** v1.1 `capture` is `capture(PaymentInfo,uint256 amount,uint256 feeAmount,address feeReceiver)` (selector 0x3efa46e1), not the v1.0 `uint16 feeBps` form, so a call built from older Commerce Payments docs reverts and CDP reports only "unable to estimate gas". We found it by reading selectors out of the bytecode. Coinbase should publish the v1.1 ABI next to the addresses, and surface revert reasons from `send_transaction` gas estimation.
- **Base Sepolia isn't listed in the binding, but the contracts are deployed there** (v1.0 and v1.1 at the documented addresses). Coinbase should say so in the spec.
